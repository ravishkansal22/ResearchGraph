This independent audit was conducted to rigorously verify the claims made in the backend implementation report for **ResearchGraph**, an evidence-grounded scientific discovery platform. 4. The reproducibility of embeddings and model registry execution.

8. The operational status of experiment design plans.

10. Repository test integrity and non-regression guarantees.

### Key Audit Conclusions
- **Software Engineering Quality: Exceptional.** All 200 automated unit and integration tests pass with 100% success rate in 22.52 seconds. The FastAPI backend is fully operational, well-structured, typesafe (Pydantic v2), and executes warm end-to-end inquiries in ~57 ms. Historical artifacts remain uncorrupted.
- **Scientific & Epistemic Claims: Require Substantial Caveats.** Several reported scientific discovery claims conflate software implementation success with scientific validation:
  - The 22 "trusted edges" in the graph are **document-containment structures** (`Paper CONTAINS Statement`), not scientific concept-to-concept relationships. **Zero trusted semantic relationships between scientific concepts exist in the graph.**
  - Retrieval benchmark ground truth is generated by a **rule-based term-matching heuristic**, not human expert annotation.
  - The discovery ablation delta of `+0.0800` is an **arithmetic artifact of discrete weighting constants** in the scorer formula, not an empirical discovery measurement.
  - Three of the 7 negative knowledge records were **inadvertently ingested from unverified Cartesian-product table relationships** due to a missing filter in `DeadEndGraveyard`.
  - The "100% false-novelty prevention rate" is a **structural schema invariant** (the `GapStatus` enum lacks a `VERIFIED_NOVEL` value) rather than an empirical benchmark outcome.

## 3. Audit 2: Research Graph Provenance & Edge Reconciliation

### 3.1 Trace of All 31 Graph Edges
The previous report claimed: *"Total Nodes: 618, Total Edges: 31, Trusted Edges: 22, Excluded Cartesian: 9"*.
The graph builder (`pipelines/graph/builder.py`) was audited line-by-line:

1. **The 22 "Trusted Edges":**
   - Constructed in lines 226–244: For every statement row in `statements`, a directed edge `edge_contain_{statement_id}` is created with predicate `GraphRelationPredicate.CONTAINS` from `paper_id` to `statement_id`.
   - These edges have `evidence_support = SUPPORTED` and `human_verification = VERIFIED`.
   - **Conclusion:** These are document structure / containment links, NOT scientific relationships between concepts.
2. **Statement-to-Entity Links:**
   - In lines 246–263, the builder attempts to add `Statement -REPORTS-> Entity` edges if `s_dict['related_entity_ids_json']` contains entity IDs.
   - In `v0.5.1/knowledge_base.db`, `related_entity_ids_json` is `[]` for all 22 statements.
   - **Conclusion:** Zero Statement-to-Entity links were created.
3. **The 9 Concept Relationships:**
   - Origin: Ingested from `relationships` table in `v0.5.1`. All 9 originate from chunk `chk_rg_doi_ebe643c2b3dd_A_0135`.
   - All 9 are marked `evidence_support = UNSUPPORTED`.
   - When `trusted_only = True`, all 9 are excluded.

### 3.2 Finding & Severity
- **Finding DISC-002 (Severity: CRITICAL):** **Zero trusted scientific concept-to-concept relationships exist in the graph.** The 22 trusted edges are purely document containment (`Paper CONTAINS Statement`). The graph cannot be used for mechanistic semantic path traversal between concepts without relying on text chunk retrieval.
- Detailed breakdown published in [graph_edge_provenance_report.md](file:///a:/Academics/AIML/Projects/ResearchGapAnalysis/ResearchGraph/research/evaluation/graph_edge_provenance_report.md).

## 4. Audit 3: Retrieval Evaluation Validity

### 4.1 Benchmark Provenance & Labeling Function
In `research/embeddings/eval_retrieval.py`:
- 8 queries are evaluated over a 500-chunk sample.
- **Relevance labels are generated automatically** by `is_relevant(text, query)` (lines 105–111):
  ```python
  def is_relevant(text: str, query: BenchmarkQuery) -> bool:
      lower = text.lower()
      if query.target_concept.lower() in lower:
          return True
      overlap = sum(1 for term in query.relevant_terms if term.lower() in lower)
      return overlap >= 2
  ```
- **Auditor Evaluation:** This is an automated **term-matching heuristic (pseudo-relevance)**, not a human-annotated scientific benchmark.
- **Built-in Bias:** Because relevance is defined by the presence of query keyword strings, BM25 naturally scores high (Precision@5: 0.600, MRR: 0.807), while dense vector retrieval (which retrieves semantically related passages using different vocabulary) is penalized as false positives.

### 4.2 Finding & Severity
- **Finding DISC-004 (Severity: MAJOR):** Evaluation ground truth is rule-based and lexically biased. Claims that dense retrieval or BM25 were validated against scientific ground truth must be qualified as pseudo-relevance baseline checks.
- Detailed breakdown published in [retrieval_benchmark_provenance_report.md](file:///a:/Academics/AIML/Projects/ResearchGapAnalysis/ResearchGraph/research/evaluation/retrieval_benchmark_provenance_report.md).

## 6. Audit 5: Discovery Algorithm Validity & Ablations

### 6.1 Scorer Mathematical Analysis
In `pipelines/discovery/scorer.py` (lines 72–80 and 104–110):
- Scoring weights: `weight_semantic: 0.25`, `weight_evidence: 0.25`, `weight_distance: 0.20`, `weight_mechanistic: 0.20`, `weight_diversity: 0.10` (Sum = 1.0).
- When cross-domain distance is enabled and domains differ: $s_{dist} = 0.90$.
- When cross-domain distance is ablated (`enable_distance = False`): $s_{dist} = 0.50$.
- Mathematical delta:
  $$\Delta = (0.90 - 0.50) \times 0.20 = 0.40 \times 0.20 = \mathbf{0.0800}$$
- **Auditor Evaluation:** The reported ablation delta of `+0.0800` is an exact algebraic identity of the piecewise constants chosen in the Python code, NOT an empirical measurement of discovery usefulness.

### 6.2 Candidate Generation Mechanism
In `pipelines/discovery/algorithms.py`:
- `discover_problem_to_method` iterates over method entity nodes in the graph and executes hybrid retrieval combining the method name and the problem query.
- Because there are zero trusted graph edges connecting methods to problems, candidate generation is essentially **retrieval-augmented entity matching**, not graph path traversal.

### 6.3 Finding & Severity
- **Finding DISC-005 (Severity: MAJOR):** The discovery ablation delta is an arithmetic property of the discrete scoring formula. Discovery is driven by text chunk retrieval rather than graph traversal.

## 7. Audit 6: Research-Gap Verification Invariants

### 7.1 Analysis of the 100% False-Novelty Prevention Rate
In `pipelines/gap_verification/schema.py`:
```python
class GapStatus(str, Enum):
    POSSIBLE_GAP = "POSSIBLE_GAP"
    EVIDENCE_AGAINST_GAP = "EVIDENCE_AGAINST_GAP"
    INSUFFICIENT_EVIDENCE = "INSUFFICIENT_EVIDENCE"
    REQUIRES_REVIEW = "REQUIRES_REVIEW"
```
- The enum does not define `VERIFIED_NOVEL`.
- In `pipelines/gap_verification/verifier.py`, the only assignable statuses are the four enum members above.
- **Auditor Evaluation:** The "100% false-novelty prevention rate" is an architectural design constraint (it is impossible for the system to emit "VERIFIED_NOVEL").
- **External Search:** External academic APIs (OpenAlex, arXiv) are not live-queried in `verify_gap()`; the system generates structured query strings for human researchers.

### 7.2 Finding & Severity
- **Finding DISC-006 (Severity: MINOR):** Architectural invariant correctly prevents false novelty, but external literature search is recommended rather than executed live.

## 8. Audit 7: Negative Knowledge, Hypotheses & Reviewer #2

### 8.1 Negative Knowledge Provenance & Data Leakage
The 7 negative knowledge records in `DeadEndGraveyard` were traced:
1. `neg_stmt_kb_stmt_094039105d32` (Limitation, Paper `rg_doi_1e4a04e65f34`) -> **Valid author-stated limitation**.
2. `neg_stmt_kb_stmt_1d8335bc5124` (Limitation, Paper `rg_doi_3e5df365b74c`) -> **Valid author-stated limitation**.
3. `neg_stmt_kb_stmt_6b667f284e34` (Limitation, Paper `rg_doi_3e5df365b74c`) -> **Valid author-stated limitation**.
4. `neg_stmt_kb_stmt_6ce7cf524604` (Limitation, Paper `rg_doi_1e4a04e65f34`) -> **Valid author-stated limitation**.
5. `neg_rel_kb_rel_9eacb770b891` (`federated learning` LIMITED_BY `computational cost`) -> **LEAKAGE: Cartesian product table artifact**.
6. `neg_rel_kb_rel_bf57d03902f7` (`ensemble learning` LIMITED_BY `computational cost`) -> **LEAKAGE: Cartesian product table artifact**.
7. `neg_rel_kb_rel_c043dbedbb58` (`machine learning` LIMITED_BY `computational cost`) -> **LEAKAGE: Cartesian product table artifact**.

**Root Cause:**
In `pipelines/negative_knowledge/graveyard.py` line 112:
```python
cur.execute("SELECT * FROM relationships WHERE relation_type IN ('LIMITED_BY', 'CONTRADICTS')")
```
The query omitted `WHERE evidence_support = 'SUPPORTED'`. Consequently, 3 unverified Cartesian relationships from chunk `chk_...0135` were ingested into the graveyard.

### 8.2 Reviewer #2 Mechanism
- `AdversarialReviewer` is a **deterministic rule-based heuristic**. It checks:
  - If evidence excerpts $\ge 3$ -> evidence score = 8.5; if 0 -> Critical weakness.
  - If vocabulary contains words like "decoupling", "gradient", "loss" -> score = 8.5.
  - If falsification criteria contains `p <` and `%` -> score = 9.5.
- Zero LLM calls are made.

### 8.3 Finding & Severity
- **Finding DISC-003 (Severity: MAJOR):** `DeadEndGraveyard` ingested 3 unverified Cartesian-product relationships due to a missing `evidence_support` filter.
- **Finding DISC-007 (Severity: MINOR):** Reviewer #2 is rule-based heuristics; overall scores are arithmetic averages, not peer-reviewed scientific validity proofs.
